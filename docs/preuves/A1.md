# A1 — Preuve du bug B1 (sur-réservation)

## Règle métier concernée

RM1 : on ne doit jamais vendre plus de billets que le stock disponible d'une catégorie.
Si la quantité demandée dépasse les places restantes, l'API doit répondre **409 Conflict**.

## Observation en débogueur (pdb)

Commande lancée depuis `qa/` (sans `-n`, pdb ne marche pas avec xdist) :

```powershell
pytest tests/api/test_booking_rules.py::test_rm1_cannot_order_more_than_available_stock --pdb
```

| Commande au prompt `(Pdb)` | Ce qu'elle montre | Valeur |
|---|---|---|
| `p vip["available"]` | Places restantes avant la commande | 3 |
| `p r.json()["items"]` | Billets commandés / catégorie | 4 billets, category_id 69 |
| `p r.status_code` | Statut HTTP reçu | **201 Created** |
| (assertion du test) | Statut HTTP attendu | **409 Conflict** |

La commande de 4 billets est acceptée alors qu'il ne reste que 3 places.

## Vérification en base (SQL)

Requête lancée à la racine du dépôt, pendant que le backend est en mode bug :

```powershell
docker compose exec db psql -U eventflow -d eventflow -c "SELECT c.name, c.quota, SUM(oi.quantity) AS reserves FROM ticket_categories c JOIN order_items oi ON oi.category_id = c.id JOIN orders o ON o.id = oi.order_id WHERE c.id = 69 AND o.status IN ('pending', 'paid') GROUP BY c.name, c.quota;"
```

Sortie :

```text
 name | quota | reserves
------+-------+----------
 VIP  |     3 |        4
(1 row)
```

La base montre **4 billets réservés pour un quota de 3** : la catégorie VIP est
sur-vendue d'une place. L'API, elle, affiche 0 place restante (voir plus bas) :
le dépassement ne se voit que dans la base.

## Code en cause

1. **`backend/app/routers/orders.py:99`**

   ```python
   if item.quantity > category_available(db, category) and not settings.seed_bugs:
       raise HTTPException(status_code=409, detail=f"Not enough stock for {category.name}")
   ```

   La condition `and not settings.seed_bugs` désactive le contrôle de stock quand
   `SEED_BUGS` est actif : le 409 n'est jamais levé, la commande passe en 201.

2. **`backend/app/services.py:47-48`**

   ```python
   def category_available(db: Session, category: TicketCategory) -> int:
       return max(0, category.quota - category_sold(db, category.id))
   ```

   Le `max(0, ...)` cache le dépassement : une fois la catégorie sur-vendue,
   les places restantes affichent 0 au lieu d'une valeur négative. Le problème
   n'est donc pas visible côté interface ni dans les compteurs.

## Conclusion

Le bug B1 est confirmé : le contrôle de stock est contourné (orders.py:99) et
l'indicateur de stock masque la sur-réservation (services.py:47-48).
