# RCA B4 : un code promo expiré est accepté au paiement

## Symptôme observé

Sur la page d'un événement, un client saisit le code promo `EXPIRED` (expiré
depuis le 22/11/2026) puis clique sur « Continuer vers le paiement ». Aucun
message « Promo code expired » ne s'affiche : la commande est créée, la remise
de 15 % est appliquée et le client arrive sur la page de paiement.

Le test `test_expired_promo_code_shows_error` échoue 3 fois sur 3.

## Impact (pour l'utilisateur, pour l'entreprise)

- **Utilisateur** : le client paie un prix qui ne devrait pas exister. Si le bug
  est corrigé plus tard, il pourrait voir sa commande remise en cause : perte de
  confiance.
- **Entreprise** : perte de chiffre d'affaires directe (15 % sur chaque billet).
  Pendant la vente flash de mercredi, un code périmé qui circule sur les réseaux
  peut être utilisé sans limite de date. Les campagnes promo ne sont plus
  maîtrisées.

## 5 Pourquoi

| Pourquoi | Réponse | Preuve |
|---|---|---|
| 1. Pourquoi le test UI échoue-t-il ? | Le message d'erreur `.notice-err` « Promo code expired » n'apparaît jamais : l'utilisateur passe directement au paiement. | Sortie pytest : `element(s) not found` (3/3). Trace : navigation `/events/28` → `/checkout/22`. |
| 2. Pourquoi aucun message ne s'affiche-t-il ? | Le front n'a aucune erreur à afficher : l'API répond **201 Created** au lieu de 400. Le défaut est dans le back, pas dans le front. | Trace, onglet Network : `POST /api/orders` → 201, `total_cents` 2975. Test API seul : `assert 201 == 400`. |
| 3. Pourquoi l'API accepte-t-elle un code expiré ? | Le contrôle de date existe mais il est désactivé : la condition contient `and not settings.seed_bugs`, donc elle est toujours fausse quand `SEED_BUGS=true`. | `backend/app/routers/orders.py:34`. SQL : `expires_at` = 22/11, avant la date du test (23/11). |
| 4. Pourquoi ce défaut n'a-t-il pas été bloqué avant d'arriver jusqu'ici ? | Le test UI qui le détecte tourne bien en CI, mais son échec n'arrête pas le pipeline : l'étape est marquée `continue-on-error: true`, le job reste vert. | `.github/workflows/ci.yml:51` (Playwright) et `:56` (Selenium). |
| 5. Pourquoi le pipeline tolère-t-il les échecs UI ? | Les tests UI ont été jugés instables : au lieu de les fiabiliser, on les a rendus non bloquants (`continue-on-error`) et on a masqué l'instabilité avec des reruns et des `sleep`. Un échec UI ne veut donc plus rien dire pour personne. | `ci.yml:51, 56` ; `test_checkout_e2e.py:10, 26` (`@pytest.mark.flaky(reruns=3)`) et `:19` (`time.sleep(2)`). |

## Cause racine

**Le processus de CI laisse passer les échecs des tests UI.** Avec
`continue-on-error: true`, un test UI rouge ne rend pas le job rouge. Le test qui
prouve B4 existe et échoue à chaque fois, mais personne n'est bloqué ni alerté.
Le défaut produit (orders.py:34) aurait été arrêté à la première PR si l'échec
UI faisait échouer le pipeline.

## Actions correctives

- **Produit** : dans `backend/app/routers/orders.py:34`, retirer
  `and not settings.seed_bugs` pour que le code expiré soit toujours refusé
  (400 « Promo code expired »).
- **Processus de test** : dans `.github/workflows/ci.yml`, remplacer les deux
  `continue-on-error: true` par `if: success() || failure()`. Les tests UI
  tournent même si les tests API ont échoué, et un échec UI fait échouer le
  job. Retirer aussi `@pytest.mark.flaky(reruns=3)` et `time.sleep(2)` de
  `test_checkout_e2e.py`, pour qu'un test rouge veuille dire « produit cassé »
  (fait dans A4).

## Comment vérifier que c'est corrigé

1. Backend en mode normal (`$env:SEED_BUGS="false"; docker compose up -d backend`),
   puis depuis `qa/` :
   - `pytest "tests/api/test_booking_rules.py::test_rm4_promo_codes[EXPIRED]"` → **passed** (400) ;
   - `pytest tests/ui/playwright/test_booking_ui.py::test_expired_promo_code_shows_error -p no:rerunfailures` → **passed** 3 fois sur 3.
2. En mode bug, pousser une branche : le job CI doit être **rouge** à l'étape
   « Tests UI Playwright ». C'est la preuve que le pipeline arrête maintenant ce
   type de défaut.
